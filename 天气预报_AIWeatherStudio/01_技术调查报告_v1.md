# AI Weather Studio 技术调查报告 v1（Phase 0）

- 日期：2026-11-17
- 范围：只读调查，没开发，没占 sons02 显卡，没安装、没下载、没改现有文件。
- 用户已定（11-17）：
  1. 目的先走「甲」：测 MiniMax H3 的表情、镜头、声音能做到什么程度，天气预报只当题材。
  2. 指向城市用「地图对准指尖」的反向做法。
- 四份原始调查在 `调查\`：A 本机资产、B sons02、C 天气数据与地图授权、D 动作口型合成。下面每条结论后面标了出处，如 `A§3` 指 A 报告第 3 节。
- 标记：**已验证**＝看到了文件、命令输出或官方原文；**待验证**＝资料或推断，没实测；**风险**＝存在风险；**要你定**＝需要用户确认。

## 1. 现有系统整体架构

- 现有系统不是一个统一的代码仓库，而是一堆目录、说明文件和按需写的脚本。**已验证** A§0
- 生成都在 sons02 上跑：ComfyUI 正式实例开在 8188 常驻，测试实例 8191 现在停着。各频道各写 Python/shell 脚本，直接调 ComfyUI 接口。**已验证** A§5、B§2
- 唯一有数据库和界面的是**幕布平台**（FastAPI + SQLite + React 19，sons02:8100）。它有分镜、时间轴、任务表和素材表，但真出片还没接上，现在只有模拟。**已验证** A§4
- 没有统一的任务队列和自动重试。显卡互斥靠 `tools\gpu_lease.sh` 加按 PID 管。**已验证** A§5
- 天气、真实地图相关的东西一样都没有。**已验证** A§7

## 2. 角色系统

- 角色有三种存法：说明文件、每个角色一个 `定版.json`（11 张套图）、集魂登记表（351 条，带 md5）。没有统一的 ID。**已验证** A§1
- 最接近「主播档案」的是幕布平台的 `character_version` 表，有正、侧、背和脸的图片字段，但没有声音字段，服装也只是一段文字。**已验证** A§1.3
- 现有角色全是古装，没有现代主播形象，要新做。**已验证**
- 主播用谁的脸：**要你定**。可以从选角库 portrait-gallery 的 1499 张脸里挑，也可以新做。

## 3. 服装库

- 第三方库 1407 套，纯 JSON，ID 形如 `SPR-0001`，分 8 类（春夏秋冬、内衣、性感、泳装、派对）。**已验证** A§2.1
- **每套只有一张无头的正面人台图，没有侧面和背面**，所以转身后衣服对不上的风险很大。**风险**
- 关键词里带「西装、衬衫、职业、通勤」的约 201 条，适不适合主播没看图。**待验证**
- 自建服装库有三视图，但只是文件夹，没跟角色绑定。**已验证** A§2.2
- 复用办法：从第三方库挑一套 → 用现成的「人台＋服装＋脸」三图配方（白晶晶姿势库用过）出主播定妆 → 用 H3 Image 设定表补出侧面和背面。11-16 测过，配角的衣服三面都对得上。**做法已验证**；用在现代装上的效果**待验证**。

## 4. 姿势库

- 全是静态图：线稿人台分 5 个角度，另有真人图和打斗视频。**没有任何 OpenPose/DWPose 关键点数据。** **已验证** A§3
- **没有「侧身、单臂伸直指向身旁大屏」这种主播姿势**，最接近的只有陆青古装「指路」。要新做。**已验证**
- sons02 上有 DWPose，带手部关键点，能从视频里提骨架、量指尖坐标。已知问题：本地这版有颜色通道颠倒、偶尔出空白骨架的 bug，线稿人台提不出骨架。**已验证** B§2.4、D§6
- 已知规律：H3 的姿势和景别跟着参考图走，提示词改不动。所以指向动作要靠参考图或关键帧给出来。**已验证** A§3、速查表

## 5. ComfyUI 和 H3 兼容性

本地有的（**已验证** B§1–2）：

- H3 视频模型：fl2va 首尾帧（全量和剪枝）、ref2va 参考图、混合版、Singularity v1.3、PRISM、viggle 换人。
- H3 Image 出图。
- H3 用的 ControlNet-Union 2.0（4.5GB），8188 原生有对应节点 `MiniMaxH3FunControlNetApply`，能喂骨架视频。
- 中间钉帧节点 `MiniMaxH3AddGuide`，这个节点还有一个**声音输入**。

固定做法有现成原件：文戏用 D 节 PRISM 参考图直出，1080P 用丁节，运镜用运镜库。

## 6. H3 全身主播生成可行性

- **能出**：单人、现代装、站在演播室，属于 H3 最擅长的「单人文戏」，比短剧简单。**推断，待验证**（没出过现代人物）。
- 1080P 一条 5 秒约 200–230 秒，进程显存 70–72 GiB，要独占显卡。**已验证** B§6
- 全身镜头里脸太小：1080P 全身站立时脸宽约 60–90 像素。**推算，待验证** D§3

## 7. H3 姿势控制可行性

- **H3 本体没有姿势控制**，官方模型卡没写。**已验证** D§1
- 外挂 ControlNet 2.0，11-09 打斗测过：动作跟着骨架走。但第 2 帧会从首帧跳到骨架姿势，道具会变形，而且只能配 fl2va 剪枝底模。**已验证（风险）**
- 首尾帧钉法管得住起止姿势，管不住中间过程。最后约 1 秒趋于静止，正好可以用来「保持指向」，但指尖会不会漂没量过。**待验证**
- **手准确指向某一点：我们一种做法都没测过。** 手部已知问题：两只手都占着会多画一只手，特写手会变形。**风险**

## 8. 地图指向的实现方案（用你定的反向做法）

1. 先出「指向」动作片段：正面站好 → 转身 → 抬右手指大屏 → 停住 1–2 秒。
2. 每段跑 DWPose，量出停住那段的指尖坐标，取中位数，同时看漂了多少。主方向用「肘 → 腕」连线，比手指点稳。
3. 程序画地图，平移、缩放，让当天要讲的城市正好落在指尖下，再叠高亮圈和城市名。
4. 主播和地图怎么合到一起：让 H3 出「主播站在一块空的纯色大屏旁边」，程序把地图贴进大屏。抠像方案还没调查。**待验证**
5. 手指异常检测：看手部关键点置信度、指节比例、手的数量、逐帧跳变。检测器本身要先拿已知的好片和坏片做反向对照。**做法是推断，待验证** D§6

## 9. 中文、日语口型同步方案

| 方案 | 现状 | 标记 |
|---|---|---|
| H3 原声（中、日都在官方 11 种语言里） | 中文用过：会念错字、自编台词、念提示词。**日语从没测过** | 中文已验证，日语待验证 |
| **H3 用录音驱动口型**（原生节点的声音输入；8191 上的 T8 插件有「录音驱动」工作流，单段约 3 秒） | **没测过**。能用的话，「我们自己的配音直接驱动 H3 说话」，就不用事后贴口型了 | 待验证，测试表重点项 |
| LatentSync 1.6 事后贴口型 | 定版在用，只改脸部，不动身体。脸宽不到约 100 像素检测不到，约 130 像素嘴会糊，侧脸贴过下唇扭曲 | 已验证（风险） |
| InfiniteTalk、Wan S2V 整帧重生成 | 会改身体动作，会破坏指向动作 | 资料，不建议 |

全身镜头说话的三种办法（**要你定**）：

1. 全身镜头按更高分辨率出，再对口型，最后缩回 1080。
2. 说话都放半身镜头，全身指地图时不说话或只说短句。
3. 不做口型，靠 H3 原声或录音驱动。

## 10. 中国与日本天气数据方案（C 报告）

**日本：没有障碍**

- 气象厅官网的 JSON 数据可以直接取，带发表时刻，东京实际取到了。**已验证**
- 《気象業務法》：**原样转述或解说气象厅的预报，不需要予報業務許可**，这是官方原文。**已验证**
- 但**不能**拿 Open-Meteo 这类模型数据当「东京明天的预报」播出，那算独自预报，要许可，从国外发也一样。**已验证**
- 警报不能自己发，要转也必须是气象厅原文。旧的警报 JSON 5 月起停更了，MVP 先不做警报。**已验证**
- 出处写法：「出典：気象庁ホームページ」加发表时刻。数据许可（PDL1.0）可以商用。**已验证**
- 风险：这个 JSON 是官网前端自己用的，不是承诺对外的接口，结构可能不预告就变。取不到、结构变了，就停止出片。**风险**

**中国：法律风险最大**

- 法规要求：只能传播气象台发布的预报，注明气象台名称和发布时间，不得改内容和结论。2025 年起的 AI 气象办法还禁止 AI 服务传播非气象台的预报。**已验证**
- **官方没有面向境外个人、可以商用的预报接口。** 第三方（和风天气等）的数据算不算「气象台的预报」，没有确认。**风险**

## 11. 推荐的视频合成架构

- **Remotion 有收费条款**：免费许可只给个人、3 人以内的营利组织和非营利组织，其余要买公司许可。**已验证（官方原文）**
- sons02 上没有 Node.js 和 Chromium，Remotion 在 sons02 跑不了。本机 Windows 和 WSL 有 Node 24。**已验证**
- 推荐：**Python（Pillow/cairo）逐帧画地图、字幕、天气图标，FFmpeg 叠主播层合成**，全在 sons02 跑。sons02 的 FFmpeg 6.1.1 带字幕库和硬件编码。不用担心许可。**已验证（环境）**
- 7 层结构照任务书分：演播室、地图、主播、数字和图标、字幕、语音、配乐。数字和地名一律程序画，H3 不画字。

## 12. Web 编辑器扩展方案

- 幕布平台能当底子：分镜表（镜头时长、景别、运镜、动作、提示词）、时间轴页、任务表（排队、运行、完成、失败）、素材按 md5 去重都已经有了。**已验证** A§4
- 缺的：真出片接口（现在 `enabled: False`）、自动重试、按依赖关系只重做受影响的镜头。
- 你定了先测能力，**这部分建议先不做**，测完再说。**要你定**
- 天气模块是放进幕布平台当一个新项目，还是另起一个网页：**要你定**，不急。

## 13. 显存与性能评估方法

- 已有实测（B§6）：H3 1080P 一条约 200–230 秒，进程 70–72 GiB；H3 Image 一张 20–36 秒，整卡约 56 GiB；Qwen 出图约 35 GiB。
- 没有实测的：LatentSync、H3 加 ControlNet、TTS 的耗时和显存。
- 方法：每条作业记起止时间、进程峰值和整卡峰值（`nvidia-smi` 每秒采样），写进每条片子旁边的说明文件，汇总进测试表。跑之前量空闲，剩不到 17 GiB 会静默出灰图。

## 15. 最大的技术风险

1. **手准确指向**：H3 没有精确控制。用反向做法绕开，但「抬手 → 停住」能不能稳、指尖漂不漂，还没测。
2. **全身镜头的口型**：脸太小，LatentSync 检测不到。
3. **日语**：H3 原声、IndexTTS 的日语都没测过，资料说 IndexTTS 日语念错的比例偏高（技术报告字错率 9.9%）。
4. **中国版的法律**：数据源和地图都有硬性规定。建议中国版 MVP 不放中国地图，用城市卡片代替；数据源要你定。
5. **服装转身后对不上**：服装库只有正面图。
6. **气象厅 JSON 会变**：要做停止出片的保护。

## 17. 验收标准

**能力测试（T1）**：每项都有客观量数和打分，挑出的样片挂幕布，你看过打分。测出来的结论分三类：能用、有条件能用、做不到。做不到的写清卡在哪。

**MVP（T2/T3）**：沿用任务书的 10 条，其中「手势指向正确城市」用反向做法保证，量的是程序算出的城市坐标和测出的指尖坐标差了多少像素。
